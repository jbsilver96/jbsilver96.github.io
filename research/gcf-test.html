The shorthand works. It's just not as short as advertised.

The Scout found GCF (Graph Compact Format), a text format for structured data that declares field names once and then sends rows of bare values. Its makers claim 50–92% fewer tokens than JSON, with nothing lost — every payload decodes back exactly — and that models read it perfectly with no instructions at all. The tank's founder greenlit a same-day test, with one condition of his own: performance must not downgrade. So we encoded three real payloads of ours in GCF — and in TOON, the rival format GCF benchmarks itself against — counted every token, decoded everything back, and quizzed a model on the data both ways.

The verdict, in two parts
Counting: PARTIAL — real savings of 26–40%, short of the claim. Performance: NO DOWNGRADE — 20/20 vs 20/20, and zero data lost.

GCF did everything it promised except the size of the saving. On our payloads it used about a quarter to two-fifths fewer tokens than JSON as it is ordinarily sent — a real, usable saving, and materially below the "50–92% fewer" headline. And a model answering questions from the GCF version got every question right, exactly as it did from JSON.

Token counts are tiktoken (cl100k_base) on the exact bytes of each encoding; ratios are against pretty JSON — the form data is actually authored and sent in our stack, and the vendor's own comparison class. Our verdict lines were frozen before the test: the counting claim holds at 0.50× or better on at least two of three payloads, is partial in the 0.50–0.80 band, and fails above that. No payload reached 0.50×, so the counting verdict is PARTIAL. GCF beat TOON on the two record payloads and essentially tied it on the page tree (4,880 vs 4,849).

The honest footnote, same rule as our OpenUI test: squeeze JSON down to its minified form and the edge mostly evaporates. Against minified JSON, GCF is 4.7% smaller on the venue records, 27.8% smaller on the event records, and 0.5% larger on the page tree. We report the headline against JSON in its normal working form — as does the vendor — but the minified numbers are here in the table, not hidden.

Why our ratios sit above the vendor's floor is the same lesson the OpenUI test taught: the saving is structural, not verbal. The venue records are prose-heavy — long descriptions dominate, and no format compresses prose. The page tree is irregular. The event records — uniform shape, repeated fields, many empty values — are closest to the vendor's benchmark data, and they produced the best ratio, 0.600×.

Nothing lost

Every payload came back exactly

The frozen design treated any silent data loss as an automatic failure for the format, whatever its token count. There was none — in either format. Decoding each encoding reproduced the original payload exactly on all three payloads, for GCF and for TOON alike: every number, null, nested list, embedded string and unicode character, checked by a key order-insensitive deep comparison. Neither format refused a payload, truncated one, or needed the data massaged first — mismatched keys between records, floats, and even a field containing serialized JSON all survived.

This deserves saying plainly, because GCF's own marketing attacks TOON for silently corrupting data. On our payloads, neither format corrupted anything. Whatever TOON's failure modes may be elsewhere, they did not appear here, and we won't repeat the attack as if our test had confirmed it — it didn't.

Performance

The model read the shorthand just as well

The founder's condition was that a cheaper format must not make the model worse at the data. So we ran a fixed battery: 20 questions over slices of the venue and event payloads — exact lookups (including a full street address), counts, filtered counts, a maximum-latitude computation, one cross-field query per payload — with every answer computed from the data in code beforehand. One model (Muse Wonder), one prompt, temperature zero; the only difference between arms was whether the data block was JSON or GCF. No format instructions were added to the GCF arm — the vendor says models read GCF natively with zero instructions, so the arm ran exactly as a real adopter following that guidance would run it.

Result: JSON 20/20, GCF 20/20. The per-question diff table is empty — no question JSON answered that GCF missed. The API's own prompt-token counts corroborated the counting arm (venue slice: 5,899 tokens as GCF vs 8,160 as JSON; event slice: 7,209 vs 11,978). Total battery spend was $0.5463, including an aborted first attempt whose scores were discarded — its output cap was consumed entirely by reasoning tokens, returning empty answers in all arms, JSON included; a bug in our battery, not a format result.

A watch item, not a finding: the GCF arms used roughly twice the reasoning tokens of the JSON arms (3,466–3,831 vs 1,590–2,386) while still using fewer total tokens per call. That is one run per cell and reasoning-token counts vary a lot run to run, so we record it unscored — but any larger trial should watch whether the model thinks longer when reading the shorthand.

Method

How the test was run

  • Payloads, and where they came from. (1) The first 200 records of the tank's venue registry (1,639 records). (2) The events pipeline's real Eventbrite staging export — 35 records, used complete. The design asked for about 100 events; this file is the local tree's only nested-shaped real event export, so it was used in full rather than padded with invented or mismatched records. (3) The OpenUI test's page component tree, as-is.
  • Encoders, verified at the source. GCF: the official Python SDK, gcf-python 2.8.0 (PyPI author "Blackwell Systems"; the package the project's own implementations table links to), generic profile. TOON: toon-format 1.2.0, the official Python implementation — a real encoder, not a hand-rolled one. GCF is open source under Apache-2.0, spec v3.5.1.
  • Counting. tiktoken 0.14.0, cl100k_base, on the exact bytes written for each encoding. The counting arm called no model and cost $0.
  • Round-trip check. decode(encode(x)) compared against x with key order-insensitive dictionary comparison and exact value equality, numbers treated as JSON numbers (2 equals 2.0). All six encodings passed.
  • The graph profile was not run. GCF's graph profile operates on graph objects (payloads of symbols and edges); converting an arbitrary JSON tree into that model would be remodeling the data, not encoding it, so it could not be round-trip-tested like-for-like. The generic profile handled the tree payload without loss.
Limitations

What this test does not show

  • Comprehension was tested at battery resolution only — 20 questions, lookups and counts on 30-record slices, one model, one run per arm. That is enough to catch a downgrade of the size the founder's rule cares about; it does not establish the vendor's "100% comprehension on every frontier model" claim, and the counting result must not be read as smuggling that claim in.
  • GCF's compounding features were not tested. The format also claims session deduplication and delta encoding across turns — sending references and changes instead of whole payloads, which is where it claims up to ~99% per-call savings. This test covers single-shot encodings only; the compounding claims remain exactly that: claims.
  • Ratios depend on the baseline. Measured against pretty JSON, GCF saves 26–40%. Measured against minified JSON, it saves little or nothing on two of three payloads. Which baseline is honest depends on what your stack actually sends — ours sends pretty JSON, so that is the headline here.
  • TOON was run with its official encoder at default settings — the same fairness rule applied to GCF.

Sources: the GCF repository (github.com/blackwell-systems/gcf, Blackwell Systems, Apache-2.0) for the format specification and claims; the toon-format project's official Python encoder; the tank's own venue registry, events pipeline staging export, and OpenUI test records for the payloads.
