Same screens, half the words — on app screens

The Scout — the tank's scout for new ideas across the AI field — found OpenUI, a compact language that lets an AI describe a screen in a shorthand instead of verbose JSON. Its makers claim the shorthand takes about half the tokens: 4,800 tokens for seven test screens, where two JSON approaches used about 10,000 each. The tank's founder greenlit a same-day test. So we built two screens both ways — a full website page and a phone app screen — and counted every token.

The finding, in one line
The saving is structural, not verbal — repeated rows compress about 2×; prose doesn't compress at all.

Both formats have to carry a screen's actual words character for character. What the shorthand squeezes is the scaffolding around them — and the more of a screen is repeated structure (rows, chips, cards), the more there is to squeeze.

The results

Two screens, two verdicts

ScreenOpenUI LangJSON (C1)RatioVerdict
Website page — a redesigned Stream Presence homepage4,632 tokens6,638 tokens0.70×PARTIAL
App screen — a phone event-discovery screen670 tokens1,341 tokens0.50×CLAIM HOLDS

For reference, the vendor's own benchmark ratio is ~0.48×. Our verdict lines were frozen before the test: a claim holds at 0.60× or better, is partial between 0.60× and 0.85×, and fails above that. On the app screen — a dense grid of repeated parts, and exactly the kind of screen OpenUI is built for — the shorthand matched the vendor's number almost exactly. On the website page, most of the tokens are long prose passages that both formats must carry word for word, so the structural saving dilutes to 0.70×. The split is itself the finding.

Where the tokens go tells the same story. One filter chip costs 10 tokens of Lang — chip3 = Chip("Free", false) — against roughly 35 tokens of nested JSON. Six event cards: 343 tokens against 576. But a paragraph of writing costs the same in both, because it is the same.

Method

How the test was run

  • One content model, two descriptions. Both versions of each screen were generated from a single content model, so neither side could win by saying less. The website's words come from this site itself — desk summaries, all 10 Scout finds, research programs and log entries carried over verbatim; the app screen's six event cards use real listings the tank's events pipeline promoted the same day.
  • The formats. Arm A: OpenUI Lang 1.0 as specified in the project's own repository — one short statement per component, references instead of nesting — against a component library of 33 parts defined for these screens. Arm B: the vendor benchmark's own JSON format (Thesys C1: nested objects with a component name and props), the same comparison class the 4,800-vs-10,000 claim was measured against.
  • Counting. Every file counted with tiktoken (cl100k_base encoder), the same tokenizer family the vendor used. JSON counted as it is actually authored and streamed — indented. The honest footnote: squeeze the JSON down to minified form and the gap nearly closes on the website page (ratio 0.95×) and narrows on the app screen (0.86×). We report the headline against JSON in its normal working form — as does the vendor — but the minified numbers are here, not hidden.
  • Equivalence check. A program stripped both rendered pages to visible text and compared them: identical on both screens (website: 222 text segments, 24 links in identical order, same dropdowns; app: 54 segments, same search placeholder). Nobody won tokens by leaving words out.
  • Render route, disclosed. OpenUI's own renderer is a React runtime inside a large monorepo; standing it up for a static test was disproportionate. Instead, the Lang was rendered by a small, faithful build-time parser written for this test, through the same component renderers and the same styling as the JSON arm — so any output difference would have been a content difference, not a renderer difference. The Lang sources are the artifacts of record.
  • Cost. $0. No model API was called in either arm; both descriptions were written locally from the content model. What the token counts measure is the cost a model pays every time it generates the screen — which is where the claim lives.
Limitations

What this test does not show

  • No live-model latency was measured. Fewer tokens should mean proportionally faster generation at a fixed decode rate — the vendor's speed claims rest on that arithmetic — but we did not time a real model streaming these screens.
  • A static page is not OpenUI's home turf. The language is built for app screens a model streams at runtime. The results show exactly that gradient: 0.50× where it belongs, 0.70× on a prose-heavy page.
  • Interactive features are untested. Our parser covers the part of the language these screens use — components, text, references. OpenUI's queries, state and actions were not exercised; a read-only screen and a marketing page need none of them.
  • The app screen is a representative surface built for this test, in the style of the event app the tank works on — not a capture of a production app.
  • Encoder note. We counted with tiktoken's cl100k_base; the vendor used a newer encoder. Both arms here share one encoder, so the ratios stand; absolute counts would shift slightly under theirs.
  • Authoring cuts both ways. The Lang is fast and readable once you know each component's prop order — but swap two same-typed arguments and nothing complains. JSON is verbose and typo-prone, yet self-describing. For a model generating at runtime, brevity is the point; for a human maintaining a page, explicitness partly pays for itself.

Sources: the OpenUI repository (github.com/thesysdev/openui, Thesys, MIT) for the Lang specification, the component-library format and the benchmark figures; this site's own pages for the website content.
