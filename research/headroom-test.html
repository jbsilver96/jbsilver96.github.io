Stream Presence · Experiment report · Oct 24, 2026

It shrank the log by 87%. Then it couldn't find the beginning.

The Scout found Headroom, a tool that compresses everything an agent reads — tool outputs, logs, files, search results — before it reaches the model, claiming the same answers for a fraction of the tokens. Its safety pitch is reversibility: the originals are cached, and the model can fetch the full text back. The tank's founder greenlit a same-day test, and we froze the verdict in three parts before running it: savings in declared bands; performance — under the founder's standing rule, a savings win with a performance downgrade is a loss for adoption, in those words; and an honest small-payload number, because Headroom's own materials document a case where a small payload got more expensive. We compressed four real payloads of ours with headroom-ai 0.41.0 (compression entirely local, $0), counted every token with tiktoken, asked one model eight ground-truth questions per payload from the raw and the compressed context, and pulled every offloaded original back.

The verdict — three parts
Savings: PARTIAL · Performance: DOWNGRADE · Small payloads: untouched

The cuts are real and one is spectacular — our harvest log shrank 86.8%, the biggest cut in the Scout's token-efficiency lane — but answers read from the compressed log alone fell to 3 of 8, against 8 of 8 from the raw log. On clean JSON the saving was 37.4% with every answer intact — yet that call's total bill rose, because the model wrote more over the dense form. And nothing was ever lost: all 48 offloaded originals retrieved verbatim. The downgrade is the price of answering without retrieving — which is why the shape that survives this test is compression with retrieval armed, never compression alone.

A payload sent the naive way is never compressed at all, which is itself a finding for anyone evaluating this tool.

The log

What survived was the middle. The questions lived at the edges.

The battery is eight questions per payload, every answer computed from the payload by code before any model call — including one planted-style obscure fact each. On the JSON payload, the compressed context matched the raw 8/8 to 8/8, obscure fact included: the count of records carrying the rarely-present merge_notes field (14) came back right from the tabular form. On the file read the contexts were identical, so 8/8 to 8/8 there proves nothing either way. The log is where the test was decided: raw 8/8, compressed 3/8.

The pattern is mechanical, not mysterious. The log crusher kept a middle window verbatim and offloaded the head and tail. Everything the compressed reader got right lives in that window — the WARNING count, the Artsy failure URL, and, with some irony, the planted obscure fact: the log's lone park_orgs ProxyError line, kept and answered correctly. (RTK, tested earlier today, deleted exactly that species of line; Headroom kept it.) All five misses live in the offloaded blocks or in lines the crusher dropped:

  • The first galleriesnow count (71) — answered 0.
  • The first ohmyrockness upsert (+155) — answered "not present".
  • The log's first timestamp — answered with the compressed log's own first line instead.
  • The bandsintown "run done" count (8) — no answer.
  • The log's last timestamp — no answer.

Two of the misses also exhausted their completion budget and came back empty; they are recorded as misses, as scored. The shape of the failure matters more than the count: a log's most-asked questions — when did this start, when did it end, what happened first — are precisely head-and-tail questions. A compressor that keeps the middle and shelves the edges is misaligned with how logs are actually read.

Reversibility

Nothing was lost. It just wasn't in the room.

Headroom's fourth claim — reversibility — held completely. In the same process as compression, we retrieved every offloaded original: all 46 of 46 retrieval markers on the JSON payload, each one a verbatim substring of the source, zero unresolved; and both of the log's hash references — one entry holding 35,373 characters that are a verbatim substring of the 35,429-character original (the log, less a small trimmed span), the other holding the 6,977-character tail block. Four inline "[… chars elided]" spans carry no hash of their own; their content is covered by the whole-log store entry. 48 of 48, byte for byte.

So the downgrade is not data loss — it is the cost of answering without retrieving. The battery's frozen method (same prompt, context only) deliberately measured that configuration, because "the model can fetch it back" is a promise a deployment has to actually wire up. A production setup that lets the model call headroom_retrieve would likely close much of the gap; that is the obvious follow-up experiment, and it is named here as untested rather than assumed. The conclusion this test does support: compression plus armed retrieval is the viable shape; compression alone is not.

The cost nuance

Fewer tokens in ≠ a smaller bill

The strangest number in the run is on the payload Headroom handled best. The JSON battery call on the compressed context cost $0.3537; the same call on raw JSON cost $0.3339 — more money for 37% fewer input tokens. The reason is visible in the usage record: the model spent 11,552 completion tokens (reasoning plus answer) working over the dense tabular form, against 6,955 on raw JSON — and at this model's prices, output bills at $20 per million against $4 for input, five times the rate. Input is the cheap direction. A format that makes the model think longer can hand back the saving, and then some, on the expensive side of the ledger.

This is the second sighting of the same effect in one day: in this morning's GCF battery, the compact-format arms generated roughly twice the reasoning tokens of the JSON arms while still using fewer tokens per call — logged there as a watch item, one run per cell. Two tests, two different compact forms, the same direction of effect. The sample is still small and completion-token behavior varies by model, so we name it a pattern, not a finding — but it is now the standing caveat for the whole token-efficiency lane: count the whole call, not just the prompt.

The file payload

P3 is UNTESTED — not a failure of the tool

The file read saved 0.0% because no compressor engaged, and the reason is environmental, not a measurement of Headroom's prose compression. Headroom's ML text compressor, Kompress-v2, needs its model (chopratejas/kompress-v2-base) from HuggingFace; in this environment HuggingFace is unreachable through the proxy — verified with a direct download attempt, which failed the same way — and Headroom logged "Kompress model not ready; requests will not be compressed" throughout. So the ML compressor never ran, on this payload or any other. P3's zero means "no compressor engaged for a raw HTML file read here"; it must not be quoted as "Headroom can't compress HTML or prose." That question remains open, and it is one reason the savings verdict is PARTIAL rather than stronger in either direction.

The small payload

The documented regression did not reproduce

Headroom's own materials document a real task where compression made a small payload cost more — +28.2% — which is why the design froze a small-payload leg with a signed number either way. Ours came back exactly 0.0%: the router classified the small shell output as recent code and protected it, byte for byte untouched. No saving, and no regression. On payloads this small, Headroom simply declines to play — which is the right instinct, and worth more than a tool that shaves every input whether it should or not.

Method & spend

How the numbers were produced

  • Tool. headroom-ai 0.41.0 from PyPI (core plus the [html, code] extras; onnxruntime 1.31.0; the [ml] stack present but its model undownloadable here, above). Apache-2.0. Compression ran fully locally and cost $0. compress() was called with model="gpt-4o", the README quickstart value; it drives only Headroom's internal estimates — the official counts are tiktoken's.
  • Payloads. All real, all ours: the first 200 venue-registry records as a JSON tool result (the same payload as the GCF test, for comparability); the whole harvest log — the design sized this at ~50–100KB, but the entire real log is 35,429 bytes / 176 lines, and it was used whole rather than padded with synthetic lines; this site's own index.html as a file read; and a ~400-token shell output.
  • Battery. One model (Muse Wonder, muse-wonder-1.0), temperature 0, one call per payload × arm carrying all eight questions under an identical prompt — per-question calls would have blown the spend cap on the 48.5k-token payload alone. Scoring is exact-match under a checker declared before any model call; ground truth was computed from the payloads by code. Completion budgets were raised only where a call demonstrably exhausted them, and the raw arm was never disadvantaged.
  • Spend. $1.7920 of the frozen $2.00 cap, all-in: $1.0748 for the six scored calls, $0.5063 for three length-exhausted first attempts at actual usage, and a $0.2108 maximum-possible allowance for one call whose usage record was lost to a client crash, counted conservatively.
Limitations

What this test does not show

  • The battery measures the compressed context alone. It does not measure the production configuration — a model able to retrieve offloaded originals — which is the very mechanism that makes the log trade reversible, and the obvious follow-up.
  • Kompress-v2 is untested (model undownloadable in this environment). Nothing here measures ML prose compression, and P3 must not be cited as evidence about it.
  • One model, one run per arm. Counting questions over 200 records are reasoning-heavy, and the completion-token behavior behind the cost nuance would vary by model and by run.
  • One log, 176 lines, from one pipeline. Log-crush behavior on larger or differently-shaped logs will differ in degree — though the head/tail alignment problem is structural, not size-specific.

Bottom line. Headroom makes the largest honest cut we have measured in this lane, keeps its reversibility promise perfectly, and knows when to leave a small payload alone. It also demonstrates the lane's central trap twice over: answers degrade when the model reads the compressed form without retrieving — and the bill can grow even when the answers don't, because output is the expensive direction. Adoptable shape, if any: structured payloads, retrieval armed, whole-call accounting. Compression alone, sold on input tokens alone, is not a saving.
